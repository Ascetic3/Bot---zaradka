# Бот клуба «Магия утра»

Telegram-бот клуба «Магия утра» на Node.js и grammY. Данные участников хранятся в SQLite.

## Требования

Установите Node.js (LTS). В PowerShell используйте `npm.cmd`, если команда `npm` заблокирована.

## Настройка

1. В этой папке скопируйте пример настроек:

   ```powershell
   Copy-Item .env.example .env
   ```

2. Откройте `.env` и замените значение `BOT_TOKEN` на токен, выданный BotFather. Не публикуйте этот файл и не отправляйте токен в чат.
   `PHONE_PROOF_SECRET` можно оставить пустым: тогда подписанные подтверждения используют ключ, производный от `BOT_TOKEN`. Для нескольких процессов укажите один и тот же отдельный секрет во всех их локальных настройках. При смене ключа незавершённым анкетам потребуется повторно подтвердить телефон и согласие.
3. Установите зависимости:

   ```powershell
   npm.cmd install
   ```

## Запуск

```powershell
npm.cmd start
```

Пока процесс работает, откройте своего бота в Telegram и отправьте `/start`. В личном чате бот показывает приветствие и главное меню. Обычная регистрация доступна только при настроенной и опубликованной политике, версии согласия и включённом флаге публикации; в деморежиме она всегда заблокирована.

Для остановки нажмите `Ctrl+C` в терминале.
### Защита выбора SQLite-базы

Обычный запуск использует `DB_PATH` или `data/club.sqlite`. До открытия базы для записи код проверяет режим запуска и, если файл уже существует, читает его служебные таблицы только для чтения. База с меткой `demo_seed_metadata` не принимается обычным ботом, даже если файл переименовали или указали через другой путь. Допустимую рабочую базу можно хранить по другому пути, если её тип безопасно подтверждён. Демозапуск закреплён за `data/demo.sqlite` и проверяет служебную метку и параметры набора; он не принимает `club.sqlite`. При неизвестном или противоречивом типе запуск останавливается до Telegram polling. Пустая рабочая база инициализируется штатно, но старые схемы не мигрируются автоматически.

## Резервное копирование SQLite

Ручную копию можно создать в любой момент, в том числе пока бот работает:

```powershell
npm.cmd run backup
```

Команда использует существующий файл из `DB_PATH` (или `data/club.sqlite`, если `DB_PATH` пуст). Если файла нет, резервирование останавливается и пустая база не создаётся. Для копирования используется `better-sqlite3.backup()`, который учитывает режим WAL. После создания копия открывается отдельно только для чтения и проверяется на целостность SQLite, внешние связи, поддерживаемую версию и ограничения схемы.

Рядом с каждой копией создаётся JSON-файл технических метаданных. В нём есть дата создания, версия схемы, тип базы (рабочая или демонстрационная), размер, SHA-256 и количество участников, аккаунтов и администраторов из одного снимка базы. Телефоны, имена, email, Telegram ID и черновики в метаданные не записываются. Контрольная сумма помогает заметить последующее изменение файла, но сама по себе не доказывает подлинность источника. Копия без успешно проверенного файла метаданных не считается пригодной для очистки или восстановления.

Готовый снимок устанавливается без перезаписи существующих файлов: сначала используется жёсткая ссылка, а если Windows или файловая система запрещает такую операцию — эксклюзивное копирование с последующей проверкой размера, контрольной суммы и SQLite. Это не заменяет SQLite Backup API: сам согласованный снимок по-прежнему создаётся через него с учётом WAL.

Перед запуском копирования программа сверяет фактический файл открытого соединения с ожидаемым путём и настройкой режима. `data/demo.sqlite` нельзя случайно обработать как рабочую базу. В демонстрационном режиме разрешён только ожидаемый путь демобазы. Копирование прекращается, если источник отсутствует или его нельзя уверенно определить.

### Настройки

Добавьте нужные значения в свой локальный `.env`:

```env
BACKUP_DIR=
BACKUP_INTERVAL_HOURS=24
BACKUP_RETENTION_COUNT=14
BACKUP_AUTO_ENABLED=true
```

- `BACKUP_DIR` задаёт папку резервных копий. Если оставить пустым, Windows использует приватную системную папку `%LOCALAPPDATA%\MagicMorningBot\backups`; на других системах — `~/.local/share/MagicMorningBot/backups`.
- `BACKUP_INTERVAL_HOURS` задаёт интервал автоматических копий. По умолчанию — 24 часа.
- `BACKUP_RETENTION_COUNT` задаёт число сохраняемых исправных копий. По умолчанию — 14.
- `BACKUP_AUTO_ENABLED=false` отключает автоматическое копирование, например на компьютере разработчика. Значение по умолчанию — включено.

Автоматическое резервирование запускается после подключения бота к Telegram: бот создаёт первую копию, затем повторяет операцию с заданным интервалом. Копии создаются только пока работает процесс бота. Если компьютер или бот выключен, новые копии не создаются. Ошибки копирования записываются в журнал только как безопасный технический тип ошибки, без текста анкет. Старые копии удаляются только если они созданы приложением и успешно прошли проверки вместе с метаданными; неисправная новая копия не удаляет предыдущие рабочие копии.

По умолчанию резервные файлы хранятся вне папки проекта. Если вы укажете `BACKUP_DIR` внутри проекта, файлы SQLite и папки `backups` игнорируются Git. Доступ к папке резервных копий должен иметь только владелец клуба или уполномоченный оператор: в копиях содержатся персональные данные.

### Ручное восстановление

Восстановление автоматически не выполняется. Безопаснее сначала восстановить копию в отдельный новый файл и проверить её. Команда откажется перезаписывать существующий путь:

```powershell
npm.cmd run db:restore -- --backup "C:\полный\путь\к\копии.sqlite" --destination "C:\полный\путь\к\восстановленной.sqlite"
```

Команда проверит SQLite и метаданные до и после копирования, создаст также sidecar JSON и не заменит рабочую базу. Только после отдельного решения о восстановлении остановите бот, сохраните текущую базу вместе с её `-wal`, `-shm` и `-journal`, затем проведите замену по утверждённой процедуре. Не подставляйте рабочий путь в `--destination`, если он уже существует.

1. Пока бот ещё работает, попробуйте сохранить текущее состояние командой `npm.cmd run backup`. Если база повреждена и команда завершается ошибкой, после остановки бота сохраните вручную текущий файл базы и все имеющиеся рядом файлы `-wal`, `-shm` и `-journal` в отдельную папку восстановления.
2. Остановите бот в его терминале сочетанием `Ctrl+C` и дождитесь завершения процесса. Не заменяйте базу, пока бот работает.
3. Выберите резервный файл `magic-morning-....sqlite` вместе с одноимённым файлом `.sqlite.json`. Для проверки используйте команду восстановления в новый путь, показанную выше. Она также сравнит checksum, размер, версию и счётчики из метаданных.

   ```powershell
   node -e "const D=require('better-sqlite3'); const d=new D(process.argv[1],{readonly:true,fileMustExist:true}); console.log(d.pragma('integrity_check')); d.close()" "C:\путь\к\копии.sqlite"
   ```

   Результат должен содержать `ok`; эта простая команда не проверяет метаданные и связи. Основную полную проверку выполняет `db:restore` при восстановлении в новый файл.
4. Сохраните нынешний основной файл базы и его WAL/SHM/journal-файлы в отдельную резервную папку. Не удаляйте их: после остановки процесса их можно переместить как единый комплект.
5. Скопируйте выбранную проверенную `.sqlite`-копию на путь рабочей базы. Резервная копия представляет собой самостоятельную базу; не переносите рядом с ней старые `-wal` или `-shm` от заменяемой базы.
6. Откройте восстановленный файл только после проверки, затем проверьте его на временном запуске/стенде. Не запускайте одновременно два бота с одним Telegram-токеном. Если возникнет проблема при отдельном согласованном восстановлении, остановите процесс и верните сохранённый комплект исходной базы.

Не выполняйте восстановление настоящей базы, пока отдельно не подтвердите это действие и не убедитесь, что сохранена исходная база.

## Версии схемы SQLite и миграции

Схема базы имеет номер `PRAGMA user_version`. Текущая версия приложения — 11. Переходы сохраняют историю: версия 1 создаёт базовые таблицы и ограничения, версии 2–4 добавляют поля согласия и username администратора, версия 5 — учёт запросов отзыва согласия, версия 6 — одноразовые запросы связывания аккаунтов, версия 7 — запросы удаления анкет, версия 8 — разрешает новый запрос после завершения предыдущего, версия 9 — отмечает тестовые анкеты демобазы, версия 10 — хранит Zoom-встречи, задания и историю доставки, а также отметки о входящих личных чатах Telegram, версия 11 — общее состояние ограничения скорости Zoom-рассылок. Каждый шаг и номер версии фиксируются транзакционно. Ошибка шага откатывает его, а завершённые предыдущие версии остаются согласованными.

Новая пустая база получает актуальную схему. Импорт модуля не обновляет существующую базу со старой схемой: приложение останавливается с сообщением о необходимости явной миграции. До миграции проверяются версия, состав таблиц и столбцов, индексы, уникальности, внешние ключи и ограничения. Неизвестная версия или структура останавливает процесс без попытки «угадать» схему.

Сначала остановите программу, которая использует выбранную базу, и выполните только предварительную проверку. Путь указывайте явно:

```powershell
npm.cmd run db:migrate -- --check --db "C:\полный\путь\к\club.sqlite"
```

Эта команда открывает файл только для чтения и показывает текущую версию и план; она не меняет базу. Перед реальным обновлением создайте проверенную копию через `npm.cmd run backup`, сохраните её и убедитесь, что присутствует sidecar `.sqlite.json`. Применять миграцию можно только после отдельного решения владельца и проверки отчёта:

```powershell
npm.cmd run db:migrate -- --apply --db "C:\полный\путь\к\club.sqlite" --confirm "C:\полный\путь\к\club.sqlite"
```

Путь в `--confirm` должен в точности повторять абсолютный путь в `--db`. Команда не создаёт отсутствующую базу. Перед применением остановите процессы бота, создайте и проверьте резервную копию, затем отдельно выполните `--check` и `--apply` для каждого файла базы. Рабочая и демонстрационная базы — разные файлы; указывайте правильный путь и не копируйте одну поверх другой. После миграции повторите `--check` и проверьте `PRAGMA integrity_check` и `PRAGMA foreign_key_check`. Для ошибки миграции не используйте `reset`, удаление столбцов или ручную правку `user_version`: сохраните сообщение об ошибке, сделайте копию файла и остановитесь до выяснения причины. Если проверка нашла неизвестную схему, миграция намеренно отказывается её менять.

### Политика обработки персональных данных

Файл docs/personal-data-policy-draft.md — внутренний черновик. Он не утверждён и не опубликован, поэтому не является действующей политикой. Перед сбором реальных анкет оператор должен заполнить все поля-заполнители, определить сроки и условия хранения, проверить документ со специалистом, утвердить его и опубликовать по общедоступному HTTPS-адресу.

Для включения реальной регистрации в локальном `.env` нужны все перечисленные ниже настройки. Тестовый HTML-документ не удовлетворяет этим требованиям:

- PRIVACY_POLICY_URL — действительный публичный HTTPS-адрес опубликованного документа.
- PRIVACY_POLICY_VERSION — идентификатор утверждённой редакции, назначенный оператором.
- PRIVACY_POLICY_PUBLISHED=true — явное подтверждение оператора, что документ заполнен, проверен и опубликован.
- PREVIEW_POLICY_URL — отдельная фактическая публичная HTTPS-ссылка для тестовой HTML-страницы демонстрационного экрана. Она не делает страницу настоящей политикой и не влияет на допуск к реальной регистрации.

Оставьте эти настройки пустыми или выключенными до завершения подготовки. Настоящий .env не менялся. Пока не выполнены все проверки, регистрация не начинает сбор анкеты и не сохраняет участника. Сообщение о согласии содержит ссылку внутри текста и две inline-кнопки. Факт, время, версия и привязанное к аккаунту HMAC-подтверждение записываются существующим механизмом. Это согласие не включает рекламные рассылки.

Не добавляйте настоящие значения .env в Git.

### Демонстрационный экран регистрации

Команда `/preview_registration` доступна владельцу и действующим администраторам только в личном чате. Права повторно проверяются во время всей демонстрационной сессии. Она показывает все вопросы и переходы анкеты, но не записывает ответы, согласия или черновики в SQLite; ответы временно хранятся только в памяти и пропадают при перезапуске. Перед вопросами отображается демонстрационный экран согласия. Для кликабельной ссылки самостоятельно опубликуйте `public/demo-policy.html` на публичной HTTPS-странице и укажите её фактический адрес в `.env` как `PREVIEW_POLICY_URL`. Если ссылки нет или она некорректна, предварительный просмотр сообщит об этом; выдуманный адрес не подставляется. Страница помечена как демонстрационная и не является действующей политикой.

Команда `/demo_registration` доступна владельцу и действующим администраторам в личном чате после запуска `demo:start`. Она сохраняет демонстрационную анкету только в `data/demo.sqlite`, используя вымышленный телефон формата `+7000000XXXX`. Такие записи маркируются отдельно, а `DEMO_TEST_ONLY_V1` не является юридическим согласием. В деморежиме обычная регистрация заблокирована даже при настроенной политике. `/preview_registration` остаётся только просмотром и ничего не сохраняет.

Тестовые анкеты доступны в профиле, поиске, списках, статистике и Excel. Их можно редактировать, запросить удаление и отозвать тестовое согласие. Все операции выполняются только в `demo.sqlite`; проверка режима повторяется непосредственно перед записью. Обычный бот откажется открывать демобазу по её служебной метке, в том числе после переименования файла. Запрос удаления рассматривается в административной панели; фактическое удаление требует отдельного подтверждения и возможно только для помеченной тестовой анкеты. Исходные 150 записей набора генератора таким способом удалить нельзя.

Для маркировки тестовых анкет добавлена миграция SQLite v9, для расписания встреч — v10. Отдельное хранилище разрешений на Zoom-приглашения не используется. Перед использованием новой версии приложения базы должны соответствовать v10; приложение не выполняет миграции автоматически. Миграции изменяют структуру, поэтому перед их применением нужна проверенная резервная копия.

### Общая логика регистрации и подтверждения аккаунта

Бизнес-правила находятся в `src/participant-service.js` и не зависят от grammY или Telegram Context. Платформенный адаптер передаёт аккаунт и подписанные подтверждения. Telegram-адаптер в `src/registration-adapters/telegram.js` создаёт подтверждение телефона только после проверки, что Telegram-контакт принадлежит отправителю. Подтверждения подписываются HMAC-ключом из `PHONE_PROOF_SECRET`; если он пуст, используется `BOT_TOKEN`. Для нескольких процессов на одном компьютере задайте одинаковый `PHONE_PROOF_SECRET`. Проверка номера действует 24 часа, после чего его нужно подтвердить заново.

Доверенный способ подтверждения номера сейчас включён только для собственного контакта Telegram; бот проверяет, что контакт принадлежит отправителю, и сохраняет подписанное временное подтверждение. Проверка действует 24 часа. Интеграция с MAX API и подтверждение владения MAX-аккаунтом не реализованы; упоминание MAX в перечне способов связи не означает, что MAX подключён. Совпадение номера само по себе не объединяет анкеты. Серверный протокол связывания аккаунтов подготовлен и защищён одноразовыми запросами и ограничениями SQLite, но пользовательского интерфейса привязки и MAX-провайдера пока нет.

Перед изменением выбранного поля база сохраняет снимок текущей анкеты. Сверка снимка, проверка согласия и итоговых полей, а также обновление выполняются атомарно в SQLite. Если другой процесс успел изменить анкету, устаревший ответ не перезаписывает новые данные: пользователь получает сообщение о конфликте и актуальную анкету, после чего может начать изменение заново.

Низкоуровневые `addParticipant`, `registerParticipant` и `linkAccount` из `src/database/index.js` сами по себе не проверяют HMAC-подтверждения. В текущем Telegram-сценарии их запись обёрнута бизнес-проверками `src/participant-service.js`; прямых вызовов этих функций из обработчиков бота нет. Не вызывайте низкоуровневые методы из новых пользовательских адаптеров. Любую будущую платформу подключайте через сервис, с отдельной проверкой достоверного подтверждения номера, согласия и привязки аккаунта.

### Первоначальная настройка владельца и администраторов

В локальном `.env` укажите Telegram ID владельца клуба:

```env
OWNER_TELEGRAM_ID=123456789
```

Замените пример чисел на фактический Telegram ID владельца. Имя пользователя (username) не используется. Если переменная не задана, никто автоматически не получает административные права. Владелец открывает `/admin` в личном чате с ботом и через «⚙️ Управление администраторами» может добавить или удалить администраторов по их Telegram ID.

### Передача и восстановление роли владельца

`OWNER_TELEGRAM_ID` используется только при первом заполнении пустой таблицы администраторов. Изменение этой переменной не меняет существующие роли и не назначает нового владельца автоматически. Если в базе остались администраторы, но нет владельца, автоматическое повышение также запрещено.

В Telegram сейчас нет команды или кнопки передачи владельца. Внутренний механизм SQLite разрешает передачу только действующему владельцу, только уже добавленному администратору и только при явном подтверждении. Операция атомарна. При передаче прежний владелец должен быть явно оставлен администратором либо удалён. Не вызывайте внутреннюю функцию напрямую без согласования обеих сторон и проверки Telegram ID; username для этого не подходит. Обычная передача пока не доступна из пользовательского интерфейса.

Если владелец потерял доступ: пока бот доступен, создайте копию командой `npm.cmd run backup`, затем остановите процесс. Независимо от Telegram подтвердите полномочия преемника по утверждённой в клубе процедуре и получите его числовой ID (его можно узнать командой `/myid` в личном чате). Передайте подтверждение и копию сопровождающему проекта. Такая аварийная процедура сейчас не автоматизирована: до неё клуб должен утвердить правила проверки личности и согласования, а сопровождающий должен провести изменение отдельной проверенной транзакцией с независимой проверкой результата. Не редактируйте `admins` вручную и не меняйте `OWNER_TELEGRAM_ID` в надежде на автоматическое назначение. Если личность преемника или полномочие на восстановление подтвердить нельзя, остановитесь и сохраните резервную копию.

## Демонстрация административной панели

Для демонстрации используется отдельная база `data/demo.sqlite`. Генератор создаёт 150 вымышленных участников, разнообразные города и даты за последние 120 дней. Почта оканчивается на зарезервированный домен `.example`, телефоны имеют синтетический код `+999`, а связанные идентификаторы начинаются с `DEMO-`. Эти данные нельзя использовать для звонков, писем или отправки сообщений. Телефоны остаются неподтверждёнными, а согласие не отмечается.

Перед запуском убедитесь, что в `.env` настроен ваш настоящий `OWNER_TELEGRAM_ID`. Перед повторным наполнением остановите демо-бот, если он сейчас запущен. Команда наполнения использует штатное назначение владельца и откажется перезаписывать базу с другим владельцем или незнакомыми данными.

В PowerShell из папки проекта:

```powershell
npm.cmd run demo:seed
npm.cmd run demo:start
```

Остановите обычный экземпляр бота перед `demo:start`: Telegram не допускает одновременную работу двух экземпляров с одним токеном. В демонстрационном процессе задан путь `data/demo.sqlite`, включён видимый баннер в `/admin`, Excel-файл получает префикс `ДЕМО_`, а автоматическое резервирование выключено. Это также не позволяет копировать демо-базу в папку резервных копий рабочей базы.

Чтобы вернуться к обычной базе, остановите демо-бот сочетанием `Ctrl+C` и запустите `npm.cmd start`. Обычный запуск использует `DB_PATH` из `.env`, а если он пуст — `data/club.sqlite`. Не запускайте оба процесса одновременно с одним Telegram-токеном.

Повторный `demo:seed` проверяет метку генератора и содержимое базы. Если набор уже цел, команда ничего не добавляет; если в файле обнаружены неизвестные или изменённые записи, заполнение прекращается без их удаления или перезаписи. Не удаляйте `data/demo.sqlite`, если в ней появились нужные вам демонстрационные изменения.



## Запланированные Zoom-встречи и рассылки

В административном меню владельца и администратора есть раздел «📅 Встречи и рассылки». Владелец или действующий администратор может создать черновик встречи, указать название, время начала, время приглашения, HTTPS-ссылку Zoom и короткую заметку, просмотреть текст, затем подтвердить расписание. Для ещё не начавшейся рассылки доступны изменение, отмена и постановка в немедленную очередь. История показывает состояние и счётчики доставки. Перед каждым действием права снова проверяются по Telegram ID и роли.

Для календарного времени обязательно задайте `CLUB_TIMEZONE` в локальном `.env` как часовой пояс IANA, например `Europe/Moscow`. Администратор вводит дату как `ГГГГ-ММ-ДД ЧЧ:ММ`; код переводит её в UTC и показывает выбранный пояс. На шагах мастера можно вернуться назад: введённые ответы сохраняются, а при изменении времени встречи время отправки проверяется заново. Некорректные и неоднозначные часы при сезонном переводе отклоняются. Разрешены HTTPS-ссылки только с `zoom.us` и его поддоменов или `zoom.com` и его поддоменов.

Задания хранятся в SQLite и подхватываются периодическим планировщиком после перезапуска. SQLite атомарно выдаёт каждое задание одному процессу; отдельная уникальность и аренда защищают выдачу получателей. В Telegram приглашаются зарегистрированные участники с действующим общим согласием, подтверждённым телефоном, связанным Telegram-аккаунтом и ранее открытым личным чатом. Предпочтительный способ личной связи не влияет на получение организационного приглашения. Уведомления содержат только информацию о деятельности клуба и Zoom-встречах; реклама и продвижение в них не включаются. Текущий интерфейс не хранит отдельный отказ от Zoom-приглашений; отзыв общего согласия и ожидающий запрос удаления исключают анкету. Исходные синтетические записи демобазы и тестовые анкеты в обычном режиме не попадают в список. Если участник ещё не открывал личный чат, ему нужно сначала написать боту; бот не пытается начать личный разговор первым.

Telegram отвечает за каждую отправку отдельно. Код считает её принятой после успешного ответа API. Все экземпляры бота используют одно исключительное право отправителя в SQLite. Право захватывается атомарно вместе с проверкой получателя, удерживается на протяжении вызова Telegram API и освобождается только после атомарной записи результата. Транзакция SQLite во время сетевого вызова не удерживается. Следующая отправка начинается не раньше чем через 50 мс после завершения предыдущей; ответ 429 до освобождения права записывает общую паузу `retry_after`. Это относится и к ответам 400/403. Ожидание права и паузы происходит вне транзакции, с повторной проверкой допуска при захвате. Резервирование доставки является моментом её начала: отзыв согласия или экстренная остановка после него не могут гарантированно остановить уже начатый сетевой вызов.

Право отправителя **не перехватывается по истечении времени**: приостановленный процесс способен возобновиться. После аварийного завершения владельца или ошибки записи результата новые отправки останавливаются до ручного восстановления; при ошибке записи сначала завершите процесс владельца. **Перед восстановлением остановите и проверьте все экземпляры бота, которые могут использовать эту же базу** — включая службу, ручной запуск и процессы на других компьютерах. Одной проверки PID на текущем компьютере недостаточно, если доступ к базе был у другого экземпляра. На том же компьютере выполните `npm.cmd run meeting:recover-sender -- --check --db "<абсолютный путь к SQLite>"`, убедитесь, что указанный PID действительно завершён, затем выполните `npm.cmd run meeting:recover-sender -- --apply --db "<тот же абсолютный путь>" --confirm "<тот же абсолютный путь>" --owner-pid <PID>`. Команда сама проверяет отсутствие процесса на этом компьютере и откажет, если владелец жив, PID изменился или компьютер не совпадает. Незавершённая доставка станет `uncertain`, а её рассылка потребует ручной проверки; отправлять её повторно автоматически нельзя. Если PID был повторно использован другой программой или владелец находился на другом компьютере, команда безопасно откажет: сначала нужно установить судьбу исходного процесса и выполнять восстановление на его компьютере. Не удаляйте строку ограничителя и не обнуляйте владельца вручную.

Только достоверные отказы Telegram можно безопасно повторять; сетевой тайм-аут, ошибка сервера или сбой SQLite после успешного ответа требуют ручной проверки и не запускают слепой повтор. Если приглашение просрочено более чем на 24 часа или встреча уже началась, автоматическая отправка прекращается; во время долгой рассылки время начала проверяется перед каждым сообщением, уже подтверждённые отправки сохраняются. Система не обещает абсолютное exactly-once: после сбоя может быть невозможно определить, принял ли Telegram сообщение.

В деморежиме получателями могут быть только явно указанные действующие администраторы, которые уже писали демоботу в личный чат. Настройте `DEMO_BROADCAST_TELEGRAM_IDS` как список числовых Telegram ID через запятую. Даже при правильном allowlist демобот никогда не использует 150 синтетических записей как получателей. Тесты подменяют Telegram API и используют только временные SQLite-файлы. MAX-отправка не реализована; данные и таблица доставки допускают отдельный платформенный адаптер в будущем, но текущая отправка работает только через Telegram.


## Ограничение частоты запросов

Бот ограничивает слишком частые действия отдельно по Telegram ID и по типу операции: повторные команды, начало и заполнение регистрации, поиск и страницы участников, статистику, Excel, предварительный просмотр и редактирование анкеты. Обычное заполнение анкеты укладывается в лимит. Кнопки отмены и выхода не ограничиваются. Лимиты по умолчанию можно переопределить в локальном `.env` переменными `BOT_LIMIT_*` из `.env.example`; значение должно быть целым числом от 1 до 10000. Не меняйте `.env` в репозитории и не добавляйте его в Git.

## Остановка бота

Остановите бота сочетанием `Ctrl+C` в PowerShell. Бот перестаёт принимать новые обновления, останавливает планировщик копий и рассылок, дожидается уже выполняющихся обработчиков, рассылок и резервирования и только после этого закрывает SQLite. Если завершение зависло дольше 30 секунд, процесс завершится аварийно с кодом ошибки; база не закрывается преждевременно, а SQLite сможет восстановить WAL при следующем открытии.

## Удаление анкеты и отзыв согласия

История схемы: запросы на удаление добавлены в v7, а в v8 изменено ограничение, чтобы после завершённого обращения можно было создать новое. Рассылки Zoom добавлены в v10, общий лимитер скорости — в v11. Текущая схема приложения — v11; все переходы выполняются только явной миграцией, после проверенной резервной копии.

В личном меню «🔗 Связанные аккаунты» Telegram-пользователь может посмотреть платформы, привязанные к своей анкете, и входящие запросы. Запрос можно одобрить или отклонить кнопками в личном чате; решение проверяется по Telegram ID и одноразовому запросу. Интерфейс и серверная схема подготовлены к платформенным аккаунтам, но интеграция с MAX API не реализована, поэтому привязка MAX в реальности пока не работает.

В текущей схеме SQLite v11 раздел «🔐 Мои данные» позволяет участнику посмотреть доступные действия, направить запрос на удаление и отозвать общее согласие. Запрос удаления требует отдельного подтверждения и создаёт запись «ожидает рассмотрения»; само обращение не удаляет данные. Пока запрос `pending_review`, повторное обращение не создаётся; после `processed` или `not_applicable` новый запрос разрешён. Внутреннее выполнение удаления атомарно закрывает ожидающий запрос и удаляет анкету; в деморежиме оно ограничено специально помеченными тестовыми анкетами, исходный набор из 150 участников защищён. Административный раздел запросов показывает тип, дату и состояние. Отзыв общего согласия закрывает обычный доступ к анкете; само по себе это не означает автоматическое удаление данных или резервных копий.

Подтверждённый отзыв согласия немедленно делает согласие неактивным. После этого обычные функции приложения не возвращают анкету для просмотра, редактирования, поиска, списка, статистики или экспорта и не разрешают обновить телефон либо привязать второй аккаунт. Участник при этом сохраняет доступ к разделу «Мои данные» и статусу запроса. Автоматическое повторное согласие не создаётся. Дата согласия и исходная анкета остаются в базе до отдельного решения оператора. Код не устанавливает сроки хранения и не делает правовых выводов.

Фактическое исполнение удаления не подключено к Telegram-кнопкам и не запускается автоматически из пользовательского запроса. Оно остаётся отдельной внутренней операцией; бот не принимает решение за клуб. Перед внедрением интерфейса исполнения владелец должен определить порядок рассмотрения обращений и основания для действий. Запрос или отзыв не переписывает резервные снимки и не удаляет ранее отправленные Excel-файлы. Копии баз и выгрузки могут содержать прежние данные, поэтому отдельно нужно определить сроки хранения и безопасное удаление этих файлов. Код не объявляет политику обработки данных утверждённой и не устанавливает юридические сроки хранения. В демонстрационном режиме запросы и изменение согласия синтетических анкет отключены.
